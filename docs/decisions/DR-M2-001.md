## Deterministic authorization

Schema is strict, bounded to 64 KiB, exact fields and typed actions. Source and target IDs are immutable version-local references. Inventory records static JSX declarations, literal options, duplicate/dynamic/spread diagnostics and a conservative local-state effect audit. Only a bounded set of React state setters, local functions and pure operations are admitted; unknown calls/effects require review. This is an intentionally incomplete capability policy, not proof of arbitrary JavaScript safety or business meaning.

One setup reference per test, one layer, source must be another AUTOMATED requirement in the same frozen Spec. CREATE_ONE is a deterministic sequence: zero rows, typed fill(s)/static select(s), exactly one audited button click, one row. Optional SELECT_TEST_ITEM admits only a bounded checkbox state transition with pre/post assertions. Setup grants only these exact steps. TEST scope is checked independently against its own hints. No recursive references or inherited capabilities. Expanded setup replay counts each use against the same global 20-step limit.

Every state-changing TEST must have observable prestate and subsequent poststate; inspection-only tests remain sample observations. Planner supplies `acceptanceClaim`, an exact nonempty substring of frozen acceptance (display only). The authorizer never adopts an LLM claim of completeness: policy m2-b-local-state-2 uses a tiny explicit adequacy registry: exact frozen single-record-removal and initial-empty-list acceptances, plus their structural count/action oracle. Those finite atomic cases can produce Requirement PASS/FAIL. All other natural-language acceptances keep test-level PASS/FAIL separate from UNVERIFIED/PARTIAL_ACCEPTANCE (or PARTIAL_TEST_FAILURE), with the original acceptance exposed. In particular, arbitrary model assertions cannot turn a good complex application into a whole-requirement FAIL. Setup failure remains UNVERIFIED/SETUP_FAILED. The registry is not a general language prover and does not prove universal inputs. Earlier policy-1 observations remain immutable and are not upgraded.

## Alternatives and threats

Rejected: relax old target scope; Planner decision:ALLOW; runtime DOM discovery to grant targets; recursive setup; arbitrary selectors/evaluate; raising 20 steps; modifying allow-forms. Threats covered include fake artifacts, identity reuse, scope propagation, unknown effects, setup conflict, type changes, duplicate targets, misleading budget claims, partial proof presented as full proof, forged evidence and interrupted execution. Missing knowledge produces REVIEW_REQUIRED/UNVERIFIED, never implicit permission.

B-01/02: separate proposal and server-only immutable authorization. B-03/04: strict audit and typed bindings. B-05/08/09: exact nontransitive setup, fresh context and honest results. B-06/07: independent typed DSL and unchanged v0.1. B-10: local only, no ECS or public release claim.

No major unresolved permission/state conflict has been identified at B.0. Unsupported expressions and ambiguous effects are rejected by deterministic rules; they do not require weakening isolation. If later evidence contradicts this, stop the affected gate and report it.
